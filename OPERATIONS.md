# Эксплуатация

## Что где живёт

| Роль | Каталог | Что внутри |
|---|---|---|
| Панель | том `panelstate` (`/var/lib/smartdns-panel`) | CA, ключ подписи манифестов, сертификат шлюза агентов |
| Панель | том `pgdata` | PostgreSQL |
| Нода | том `agentstate` (`/var/lib/smartdns-agent`) | `identity/`, `revisions/<id>/`, симлинки `active` и `previous`, `state.json` |

Data plane монтирует том ноды только для чтения. Записывает туда исключительно
агент.

## Модель применения конфигурации

```
панель: fetch → parse → normalize → validate → diff → compile → sign
агент:  download → verify signature → verify sha256 → stage → validate
        → atomic symlink swap → data plane reload → report
```

Переключение симлинка атомарно. Процессы `dns-frontend`, `sni-proxy` и
`egress-relay` опрашивают файл раз в две секунды и подменяют скомпилированные
матчеры под мьютексом: активные соединения не рвутся, контейнеры не
перезапускаются, Docker socket не нужен.

Если новый артефакт невалиден, агент оставляет прежний. Больше трёх попыток
за десять минут — нода переходит в `degraded` и ждёт другой ревизии; data plane
всё это время работает на last-known-good.

## Один IP и порт 443

DoH и управляемый HTTPS не могут одновременно занять TCP/443 на одном адресе.
Варианты по убыванию предпочтительности:

1. **Два публичных IP** (рекомендуется). `DNS_IP` — 53/853/443 для DoH,
   `PROXY_IP` — 443 для прокси. Задаются в `.env` ноды.
2. **DoH на другом порту.** `DOH_PORT=8443`; клиенты получают
   `https://dns.example.net:8443/dns-query`. Некоторые корпоративные сети
   режут нестандартные порты.
3. **SNI-мультиплексор перед обоими.** nginx stream с `ssl_preread`:

```nginx
stream {
    map $ssl_preread_server_name $upstream {
        dns.example.net  127.0.0.1:8443;   # DoH frontend
        default          127.0.0.1:9443;   # sni-proxy
        ""               reject;            # без SNI не пропускаем
    }
    server {
        listen 443;
        ssl_preread on;
        proxy_pass $upstream;
        proxy_connect_timeout 3s;
    }
}
```

Имена для health-проверок и админки не должны попадать в `default`, иначе они
уедут в прокси.

**UDP/443 (QUIC) обычным SNI-мультиплексором не делится.** Режим по умолчанию —
`disabled_fallback`: ingress не слушает UDP/443, браузер откатывается на TCP.
Для `proxy` нужен отдельный IP либо QUIC-aware диспетчер, и включать его можно
только после сквозной проверки конкретного сервиса в Chrome, Firefox и Safari.

## Списки правил

Порядок объединения фиксирован:

```
effective = (объединение включающих источников ∪ ручные добавления)
          − объединение исключающих источников
          − ручные исключения
```

Суффикс сравнивается по границе метки: `example.com` покрывает
`api.example.com` и сам `example.com`, но не `notexample.com`.
`*.example.com` превращается в суффикс `example.com` вместе с apex.
Regex выключен по умолчанию; при включении используется RE2 — линейное время,
без катастрофического бэктрекинга, длина не больше 256 символов.

Порог ручного подтверждения: удалено больше 30% или добавлено больше 1000
записей, либо любой источник упал, либо непустой список стал пустым.

**Слишком широкий суффикс дорого стоит.** `google.com` уведёт через egress
почту, карты и обновления, сломает локальный CDN и увеличит трафик.
**Слишком узкий — ломает вход.** Нужны домены API, аутентификации и статики.
Если сервис перестал работать после сужения списка, начните с сетевой вкладки
браузера: она покажет недостающие зависимости.

## Управление нодами (push)

Панель сама подключается к каждой ноде на порт **3333** (HTTP/JSON поверх mTLS):
толкает конфиг при сборке ревизии и опрашивает здоровье раз в ~10 с. Ноды наружу
не звонят. Нода застряла на старой ревизии — панель видит дрейф по версии в
ответе о здоровье и дотолкивает.

**Фаервол:**

| Сервер | Порт | Открыть кому |
|---|---|---|
| любая нода | 3333/tcp | только IP панели |
| egress | relay (8443/tcp) | только IP ingress-нод |
| ingress | 53 udp+tcp | только своя VPN-подсеть |
| ingress | 853/tcp, 443/tcp | из интернета (DoT, DoH, прокси) |

Порт 3333 закрыт двумя рубежами: фаервол по IP панели и mTLS с пином её
клиентского сертификата. Открытый всему миру 53 — открытый резолвер, наружу его
не выставляют.

**Переезд панели.** Ключ CA и клиентский сертификат панели лежат в её state-томе
и попадают в бэкап. Панель, восстановленная на новом сервере, предъявляет тот же
сертификат — ноды доверяют по отпечатку, не по адресу. Переезд: восстановить
бэкап → сменить `ALLOW <IP>` для 3333 на всех нодах → перевести DNS-запись.

## Наблюдение

Метрики Prometheus: панель `/metrics` на 8080, ноды на 9101 (DNS), 9102 (прокси),
9103 (relay), 9104 (агент).

Ключевые ряды:

| Метрика | О чём |
|---|---|
| `smartdns_dns_queries_total{kind}` | доля `managed` против `recursive` |
| `smartdns_dns_synthesized_total` | сколько ответов подменено, по сервисам |
| `smartdns_dns_rejected_total{reason}` | `acl`, `rate_limit`, `concurrency` |
| `smartdns_dns_duration_seconds` | гистограмма задержки frontend |
| `smartdns_ingress_rejected_total{reason}` | `sni_not_managed` — попытки использовать как открытый прокси |
| `smartdns_tunnel_connect_total{result}` | здоровье туннеля до egress |
| `smartdns_egress_requests_total{result}` | `denied` — попытки выйти за allowlist |
| `smartdns_egress_failover_total` | переключения между egress-нодами |
| `smartdns_panel_jobs_total{type,result}` | фоновые задачи панели |

Готовый дашборд: `docs/grafana-dashboard.json`.

Алерты (`docs/alerts.yml`): heartbeat старше 60 с, расхождение ревизий дольше
10 минут, недоступность всех egress сервиса, список правил не обновлялся дольше
двух интервалов, сертификат истекает меньше чем через 14 дней, диск больше
80/90%, всплеск отказов DNS, повторяющиеся откаты, устаревшая резервная копия.

## Логи

Все пять процессов пишут JSON в stdout одинаково: поля `time`, `level`, `msg`,
`component` и дальше пары ключ-значение. Читать через `docker compose logs`,
собирать любым сборщиком, который умеет json-file.

### Уровни

| Уровень | Что попадает |
|---|---|
| `error` | только сбои, требующие вмешательства |
| `warn` | плюс отказы по allowlist, недоступность egress, неудачные задачи |
| `info` | плюс запуск, применение ревизий, регистрация нод — рабочий режим |
| `debug` | плюс имена доменов, решения по каждому соединению, ошибки записи DNS |

Где задаётся, в порядке приоритета:

1. **`LOG_LEVEL` в `.env` на самом хосте.** Побеждает всегда. Так отлаживают
   одну ноду, не трогая остальные: панель не переопределит это значение.
2. **Панель, Настройки → Логирование.** `log_level` меняет уровень панели сразу,
   без перезапуска. `node_log_level` уезжает на ноды со следующей ревизией и
   применяется горячей перезагрузкой — контейнеры не рестартуют.

По умолчанию `LOG_LEVEL` пуст: это и означает «уровнем управляет панель».

### Почему логи не растут

Три ограничителя, все включены по умолчанию:

- **Успешные запросы к API не пишутся на `info`.** Агент опрашивает панель
  каждые 15 с; при десяти нодах это больше сотни тысяч строк в сутки, в которых
  тонет всё остальное. Изменения записаны в журнал аудита подробнее, а счётчики
  запросов есть в метриках. Ответы 4xx пишутся как `warn`, 5xx — как `error`.
- **Повторы сворачиваются.** Одинаковая строка уровня `info` и выше пишется раз
  в минуту; следующая несёт поле `suppressed` — сколько повторов проглочено.
  Тысяча отказов по allowlist за минуту даёт одну строку, а не тысячу.
  Отключается через `LOG_THROTTLE=off`, когда нужно видеть каждое событие.
- **Ротация Docker.** У драйвера `json-file` по умолчанию нет предела, и
  болтливый контейнер рано или поздно забивает диск. В Compose задано
  3 × 10 МиБ на контейнер (`LOG_MAX_SIZE`, `LOG_MAX_FILE`).

На `debug` первые два ограничителя не действуют: включили — видите всё.

### Что в логи не попадает никогда

Полные DNS-запросы (qname), адреса клиентов резолвера и содержимое трафика.
На `debug` ingress пишет SNI проксируемых соединений — это метаданные о том,
что человек открывает. Поэтому `debug` — режим для короткого разбора проблемы:
включили, воспроизвели, вернули `info`.

## Резервное копирование

Контейнер `backup` в Compose панели снимает дамп раз в сутки и хранит копии
14 дней. Ручной запуск: `BACKUP_PASSPHRASE=… scripts/backup.sh`.

В копию входят: дамп PostgreSQL, CA панели, ключ подписи манифестов, сертификат
шлюза агентов. Журналы не входят.

**RPO 24 часа, RTO 2 часа** для персональной установки. Восстановление
проверяется не реже раза в квартал: `scripts/restore.sh <файл>`.

Без панели ноды продолжают работать на last-known-good, но управление не
восстановится само. При восстановлении на другой машине сохраните тот же
ключевой материал — иначе ноды придётся регистрировать заново.

## Обновление

```bash
scripts/upgrade.sh /opt/smartdns-panel
```

Порядок: резервная копия → сборка образов → обновление панели → проверка
health → ноды по одной, начиная с одной ноды каждой роли. Миграции только
вперёд, схема expand/migrate/contract: несовместимые изменения не выпускаются
в одном релизе. Откат образа безопасен, откат необратимой миграции — нет,
поэтому перед обновлением обязательна копия.

## Приёмка перед выпуском в работу

- [ ] Чистая машина ставит панель по документации без ручной правки файлов.
- [ ] Ingress и egress регистрируются одноразовым токеном и становятся healthy.
- [ ] Управляемое имя возвращает IP ingress, обычное — настоящий IP.
- [ ] Клиент видит сертификат origin, а не наш.
- [ ] Тестовый origin фиксирует IP egress.
- [ ] SNI вне списка и приватный destination не проксируются.
- [ ] Одна ревизия управляет DNS, маршрутизацией ingress и allowlist egress.
- [ ] Битое обновление списка не заменяет активную версию.
- [ ] При отказе основного egress новые соединения идут через резерв.
- [ ] Панель выключена на час — трафик идёт.
- [ ] Сломанная ревизия откатывается.
- [ ] DoH, DoT и обычный DNS проходят проверку совместимости.
- [ ] AAAA публикуется только после сквозной проверки IPv6.
- [ ] Восстановление из копии проверено.

Матрица реальных устройств: Android (мобильная сеть и Wi-Fi), iOS (мобильная
сеть и Wi-Fi), macOS, Windows, OpenWrt. Для каждого: обычный и управляемый
домен, вход и статика в приложении, принадлежность сертификата origin,
наблюдаемая страна egress, сохранение IP провайдера для неуправляемых имён,
поведение при включённом и выключенном QUIC, отказ и восстановление ingress,
отказ и восстановление egress, час без панели.

## Бюджеты производительности

| Показатель | Цель |
|---|---|
| Задержка frontend без рекурсии, p95 | < 10 мс |
| Синтезированный ответ, p99 | < 5 мс |
| CRUD control API, p95 | < 300 мс |
| Компиляция 1 000 000 записей | < 60 с |
| Одновременные TCP-соединения на ноду | 10 000 (при `ulimit -n` не ниже 65536) |

Это цели, а не SLA: фактические пределы даёт нагрузочный тест на вашем железе.
Стартовый минимум: панель 2 vCPU / 2–4 ГиБ, нода 1 vCPU / 1 ГиБ.

### Память: измерено на стенде

Холостой ход, набор правил лабораторного размера:

| Контейнер | RSS |
|---|---|
| `postgres` | 26 МиБ |
| `unbound` | 18 МиБ |
| `dns-frontend` | 15 МиБ |
| `sni-proxy` | 12 МиБ |
| `egress-relay` | 13 МиБ |
| `panel-api` | 9 МиБ |
| `node-agent` | 6 МиБ |

Итого ingress-нода ≈ 51 МиБ, egress-нода ≈ 19 МиБ, панель с базой ≈ 36 МиБ.

Сверху добавляются две величины, растущие с нагрузкой:

- **Правила** — около 75 байт на запись, в каждом процессе, который держит
  список (`dns-frontend`, `sni-proxy`, `egress-relay`). Измерено: 100 000
  правил → 7,4 МиБ, 500 000 → 49,5 МиБ. Во время применения ревизии старый и
  новый списки существуют одновременно, поэтому пик вдвое выше.
- **Соединения** — 2 × 32 КиБ буферов копирования на соединение плюс буферы
  TLS, порядка 100 КиБ на активное проксируемое соединение и столько же на
  egress-стороне. 1 000 одновременных соединений ≈ 100 МиБ на ноду.

Отсюда практический ориентир: ingress с набором на 100 000 правил и тысячей
активных соединений укладывается в 512 МиБ, но 1 ГиБ оставляет запас на пик
применения ревизии.
Следите за `nf_conntrack_max` на нодах с большим числом соединений.
