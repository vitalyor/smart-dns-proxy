Egress можно поднять на скольких угодно нодах флота — каждая даёт свою страну выхода. В раскладке сервиса вы выбираете, через какую из них уводить домены. Ingress пока один (Питер); когда захочется отказоустойчивости — добавляется вторая ingress-нода, и компилятор кладёт оба адреса в конфиг каждого устройства (multi-A). Это уже проверено в стенде.

Два порта управления (3333) и relay (8443) закрываются на уровне пакетов по IP — вторым рубежом поверх mTLS, ровно как ALLOW на remnanode. Устройствам открыты только 443/853/8443; обычный 53 — лишь тем, кто уже в вашем AmneziaWG. Открытого резолвера мы не создаём: спецификация продукта это прямо запрещает.

Осталось выбрать до первой команды

Три решения за вами

Решение A

Где живёт панель

  • советуюНода-панель Remnawave, 88.216.70.241. Там уже 2 vCPU, уже стоит nginx, который отдаст UI по panel.nolim.cloud как ещё один сайт. Control plane трафика юзеров не несёт — его география и юрисдикция безразличны. Ноды переживают отключение панели на last-known-good, это проверено.
  • вариантДомашняя лаба, 10.9.9.4. 8 ядер, 15 ГБ, порт 53 свободен — с запасом. Наружу UI отдаётся через NPM на bg.ru по awg-туннелю. Минус: панель должна доставать ноды по 3333 — из лабы это идёт через тот же туннель, лишнее звено, которое может упасть.
  • вариантСтарый сервер с NPM (bg.ru). Панели порт наружу не нужен вовсе — встаёт за NPM как поддомен. Годится, но памяти там впритык (380 МиБ свободно), а держать control plane на самой заметной RU-ноде — не лучший выбор.
Решение B

Какая нода — первый egress

Это выбор страны выхода для первого сервиса, а не архитектуры: egress можно добавить на любую ноду позже. 8443 свободен на всех.

  • советуюcs.nl — 84.32.104.6. Нидерланды, близко к РФ по задержке, чистая репутация IP под большинство сервисов.
  • вариантint.pl 95.85.254.125 · 1c.de 64.188.83.63 · cs.us 88.216.68.214. Польша / Германия / США — берите под конкретный сервис, которому нужна именно эта страна.
Решение C

Сертификат для DoT и DoH

На чистом Питере NPM нет — 853 (DoT) и 8443 (DoH) терминируют TLS сами, им нужен настоящий сертификат на имя dns.nolim.cloud. SNI-прокси на 443 сертификат не терминирует — он читает SNI и пробрасывает, ему cert не нужен.

  • советуюcertbot DNS-01 через Cloudflare. Зона nolim.cloud на Cloudflare — выпуск и продление идут по API, без открытого 80 и без остановки прокси. Сертификат кладётся в том, монтируется ноде, deploy-hook перекладывает при продлении.
  • на потомСамоподписанный для проверки. Флаг ALLOW_SELF_SIGNED_TLS=1 в .env ноды — поднять и проверить путь за минуту, до выпуска настоящего. В прод так не оставляем.
После того как A, B, C выбраны — по порядку

Установка по фазам

00Код на серверы и лимиты ядрамак + все ноды

Install-скрипты собирают образы из исходников рядом с собой. Значит на сервер нужно занести репозиторий (приватный GitHub → clone). На чистом Питере и панели сборка на месте нормальна. На egress-ноде флота (1 vCPU, ~1 ГБ) сборка Go тяжеловата — соберите образ один раз и перенесите готовым.

# мак: приватный репозиторий
git init -b main && git add -A && git commit -m "SmartDNS 2.0.0"
gh repo create smart-dns-proxy --private --source=. --push

# тесная egress-нода: не собирать на ней, а привезти образы
docker compose build              # на маке/панели
docker save smartdns/node:2.0.0 | ssh egress 'docker load'

И на каждой ноде — лимиты под тысячи соединений. Сейчас nf_conntrack_max обычно 8192, а ulimit -n — 1024; для нагрузки этого мало.

cat > /etc/sysctl.d/99-smartdns.conf <<'EOF'
net.netfilter.nf_conntrack_max = 262144
net.core.somaxconn = 4096
EOF
sysctl --system
01Панельпо решению A

UI слушает 8080 открытым HTTP — перед ним обязателен TLS. На ноде-панели это делает уже стоящий remnawave-nginx (proxy host на 127.0.0.1:8080). Входного шлюза у панели больше нет — она исходящий клиент, наружу открывать нечего.

bash <(curl -fsSL https://<хост>/install.sh) --role panel \
  --public-url https://panel.nolim.cloud \
  --admin-email vitalikmen1997@gmail.com

# пароль печатается в журнал ровно один раз
docker compose -f /opt/smartdns-panel/docker-compose.yml logs panel-api \
  | grep -A3 'Учётная запись'

Одна команда install.sh сама проверит порты, диск, время и Docker и остановится, если что-то занято. <хост> — raw публичного репозитория; из склонированного репозитория то же самое: sudo bash install.sh --role panel ….

Ключевой материал — CA и клиентский сертификат панели — лежит в томе panelstate и едет в бэкапе. Именно им панель доказывает нодам, что это она; поэтому переезд панели не требует перевыпуска ничего на нодах (фаза 06).

02Ingress212.67.10.15 · Питер

В панели: Ноды → Добавить ноду → ingress, вписать адрес управления 212.67.10.15:3333, скопировать бандл (base64 — в нём TLS-личность ноды и пин панели, как SECRET_KEY у remnanode).

bash <(curl -fsSL https://<хост>/install.sh) --role ingress \
  --bundle <BASE64 из панели> \
  --panel-ip 88.216.70.241

Скрипт проверит, что 53/443/853/8443 свободны (иначе остановится и покажет, кто их держит — ничего не отбирая), поднимет контейнеры и сам откроет 3333 только для IP панели. Имя ноды берётся из бандла — задавать его в команде не нужно. Дальше — сертификат (решение C) и порты устройствам:

# сертификат dns.nolim.cloud через Cloudflare DNS-01
certbot certonly --dns-cloudflare \
  --dns-cloudflare-credentials /root/.cf.ini -d dns.nolim.cloud

# прописать его ноде в /opt/smartdns-node/.env
TLS_DIR=/etc/letsencrypt/live/dns.nolim.cloud
TLS_CERT_FILE=/etc/smartdns/tls/fullchain.pem
TLS_KEY_FILE=/etc/smartdns/tls/privkey.pem

# порты устройствам
ufw allow 443/tcp                              # SNI-прокси (managed HTTPS)
ufw allow 853/tcp                              # DoT — основной путь, Android
ufw allow 8443/tcp                             # DoH
ufw allow from 10.9.9.0/24 to any port 53      # обычный DNS — только своим

DoT на 853 — главный путь для устройств (стандартный порт, Android Private DNS берёт его сходу). DoH на 8443, потому что 443 занят SNI-прокси; клиенту адрес указывается с портом. Захотите DoH на чистом 443 — это второй IP для прокси, как в комментарии к compose.

03Egressпо решению B · флот

Самая простая фаза: конфликтов портов нет, ставится рядом с remnanode.

bash <(curl -fsSL https://<хост>/install.sh) --role egress \
  --bundle <BASE64 из панели> \
  --panel-ip 88.216.70.241 --relay-port 8443

# relay открыт ТОЛЬКО для ingress — иначе это открытый прокси
ufw allow from 212.67.10.15 to any port 8443 proto tcp \
  comment 'relay from ingress-spb-01'

Relay и так требует клиентский сертификат ноды и проверяет домен по allowlist — но правило на уровне пакетов стоит копейки и закрывает порт от всех, кроме ingress.

04Первый сервис и приёмкапанель + телефон

В панели есть Быстрый старт: набор правил → сервис → группы → сборка ревизии → выкат. Собрали ревизию — панель тут же протолкнёт конфиг на ноды по 3333, здоровье опрашивает каждые ~10 с. Перед первой ревизией выставьте:

  • Режим доступа к DNS — restricted-public-dot для Android либо doh-профиль для iOS. Списком IP не выйдет: у телефонов адрес меняется.
  • Публиковать AAAA — нет. IPv6 на нодах нет, а Happy Eyeballs предпочтёт его: включите — часть запросов начнёт молча падать.
  • Уровень логов нод — info. На debug ingress пишет SNI каждого соединения; это для разбора, не для постоянной работы.
  • Egress группы — выбрать ноду из решения B; ingress-адрес 212.67.10.15 компилятор подставит в конфиг устройств сам.

Приёмка — с телефона, а не из панели:

dig +short <управляемый-домен> @212.67.10.15   # вернёт адрес ingress
dig +short example.org @212.67.10.15           # вернёт настоящий адрес
curl -s https://<домен>/ -o /dev/null -w '%{remote_ip}\n' # выход через egress
05Бэкап и переезд панелипо требованию

Ради чего всё это и переписывалось. Панель уезжает на новый сервер без перевыпуска чего-либо на нодах — ноды доверяют по отпечатку сертификата панели, а не по её IP.

Прямо из интерфейса: на старой панели Настройки → Резервная копия и перенос → Скачать копию (задайте пароль). На новом сервере поставьте голую панель скриптом, войдите, и там же Восстановить → загрузите файл. Панель перезапустится уже с прежними CA, ключами и базой — переустанавливать и настраивать заново ничего не нужно. Копии автоматически снимаются ежедневно; скачать можно и свежую автоматическую. Тот же файл принимает и CLI ниже — форматы едины.

# копию везём с собой (шифрована паролем из .env старой панели)
scp /var/backups/smartdns/smartdns-*.tar.enc root@новый:/tmp/

# на новом сервере — установка И восстановление одной командой
BACKUP_PASSPHRASE=<из .env старой панели> \
bash <(curl -fsSL https://<хост>/install.sh) --role panel \
  --public-url https://panel.nolim.cloud \
  --admin-email vitalikmen1997@gmail.com \
  --restore /tmp/smartdns-<...>.tar.enc

# на КАЖДОЙ ноде — впустить новый IP панели, убрать старый
ufw allow from <новый-IP> to any port 3333 proto tcp
ufw delete allow from <старый-IP> to any port 3333 proto tcp

# DNS: panel.nolim.cloud → новый адрес

Пока панель переезжает — ноды обслуживают последний конфиг с диска. Простоя у пользователей нет.

панель

UI открывается по HTTPS, в списке нод обе — ingress и egress — со статусом жива и свежей версией конфига.

управляемый домен

прямой домен

фаервол

3333 и 8443 отвечают только с нужных IP; с чужого — таймаут.

фолбек

Останови панель — ноды продолжают отвечать; подними — конфиг сам догоняется по версии.

Границы

Чего в плане намеренно нет

  • Сама установка не запущена — по вашему слову «всё кроме установки». Код готов и проверен в стенде; фазы выше — то, что делается руками в проде.
  • Локальный фолбек SNI (прокси делит 443 с NPM на одном IP) — не писал. Он нужен только если ingress придётся сажать на забитый сервер без второго IP; на чистом Питере не требуется.
  • Второй ingress для отказоустойчивости — код готов (multi-A проверен), но в этот план не входит: поднимается тем же скриптом, когда понадобится.
  • DoH на чистом 443 — оставлен на 8443. Перенос на 443 = второй IP для SNI-прокси, отдельное решение.
