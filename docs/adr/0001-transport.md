# ADR 0001. Транспорт ingress → egress

**Статус:** принято · **Дата:** 2026-08-26

## Контекст

ТЗ требует один явно зафиксированный и протестированный защищённый профиль
между ingress и egress; базовым назван VLESS поверх TLS/Reality в sing-box,
с оговоркой «либо иной один явно зафиксированный и протестированный профиль».

Данные, которые идут по туннелю, уже зашифрованы: это TLS-сессия клиента с
настоящим origin. Туннель должен обеспечить аутентификацию пиров и передать
одно поле — сниффнутое назначение.

## Решение

Собственный профиль на стандартной библиотеке Go: **TLS 1.3 с взаимной
аутентификацией сертификатами внутреннего CA панели, ALPN `smartdns/1`, затем
кадр CONNECT** (версия, команда, длина имени, имя, порт) и байтовая пересылка.

## Альтернативы

- **sing-box с VLESS/Reality.** Даёт маскировку под чужой TLS-хендшейк, что
  ценно против активного зондирования. Цена: внешний бинарник с быстро
  меняющейся схемой конфигурации, генерация конфигов под конкретную версию,
  и — главное — решение о допустимости назначения принимает чужой код.
- **WireGuard.** Даёт сеть, а не адресное назначение: пришлось бы восстанавливать
  destination на egress отдельным механизмом.

## Последствия

- Нет внешних зависимостей data plane, нет риска расхождения схемы конфигурации.
- Allowlist проверяется нашим кодом сразу после разбора кадра, до любого resolve
  и connect — это ровно то место, где предотвращается open proxy.
- **Мы не получаем маскировку Reality.** Наблюдатель видит TLS-соединение с
  клиентским сертификатом на нестандартном порту. Порт relay закрывается
  межсетевым экраном для всех адресов, кроме ingress-нод.
- Профиль пригоден к замене: `shared/tunnel` — единственное место, где живёт
  протокол.
