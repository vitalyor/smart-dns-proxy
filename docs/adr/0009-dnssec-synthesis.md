# ADR 0009. Семантика DNSSEC для синтезированных ответов

**Статус:** принято · **Дата:** 2026-08-26

## Контекст

Мы возвращаем адрес ingress вместо настоящего. Подписать этот ответ ключом
исходной зоны невозможно. Валидирующий клиент, доверяющий нашему резолверу,
должен получить честный сигнал.

## Решение

- Синтезированный ответ **никогда не выставляет флаг AD** и не копирует его из
  стороннего ответа.
- Обычные домены обслуживает Unbound с полной валидацией DNSSEC: bogus-ответ
  становится `SERVFAIL`, а не подделкой.
- Для управляемого домена подавляются записи HTTPS и SVCB (типы 64 и 65):
  подсказки `ipv4hint` и `ech` позволили бы клиенту обойти ingress.
- Для управляемого домена не выдаются CNAME, NS и SOA в ответе — только NODATA
  с SOA в секции полномочий, иначе клиент ушёл бы мимо ingress.
- AAAA публикуется только при полностью проверенном IPv6-пути; иначе NODATA,
  но никогда поддельный IPv6.

## Альтернативы

- **Выставлять AD на синтезированных ответах.** Прямая ложь валидирующему
  клиенту.
- **Проксировать HTTPS/SVCB как есть.** Клиент получил бы адрес origin и пошёл
  бы напрямую, обойдя всю систему.

## Последствия

- Клиент с локальным валидатором и собственным доверием к корню не сможет
  проверить наш синтезированный ответ — это неизбежное следствие модели.
- Ограничение зафиксировано в README и в интерфейсе.

## Тест

`TestManagedDomainReturnsIngressAddress` проверяет отсутствие AD;
`TestHTTPSRecordIsSuppressedForManagedDomain` — подавление типа 65;
`TestAAAAWithoutIPv6PathIsNodata` — NODATA с SOA вместо поддельного адреса.
