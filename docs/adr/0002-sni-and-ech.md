# ADR 0002. Восстановление назначения из SNI и поведение при ECH

**Статус:** принято · **Дата:** 2026-08-26

## Контекст

DNS-подмена лишает нас настоящего IP назначения: клиент приходит на ingress.
Единственный источник имени — SNI в TLS ClientHello. При Encrypted ClientHello
внутренний SNI недоступен.

## Решение

Ingress считывает ClientHello без терминации TLS (`shared/sniff`), берёт
`server_name`, прогоняет через IDNA и нормализацию, сравнивает с матчером
активной ревизии и передаёт исходные байты дальше без изменений.

Отклоняются: отсутствующий SNI, IP-литерал, имя вне набора правил, ClientHello
больше лимита пред-чтения, отсутствие ClientHello за 3 секунды.

**При ECH соединение отклоняется.** Трафик с неопознанным назначением никогда
не отправляется на «origin по умолчанию».

## Альтернативы

- **Прокси по умолчанию для неопознанного трафика.** Превращает ingress в
  открытый прокси. Отвергнуто.
- **Выделенный IP или IPv6-адрес на сервис.** Восстанавливает назначение по
  адресу подключения и решает проблему ECH. Требует пула адресов; оставлено
  как путь развития — архитектура этого не исключает.
- **Терминация TLS.** Требует MITM. Прямо запрещено ТЗ.

## Последствия

- Сервис с обязательным ECH не объявляется поддерживаемым.
- Проба различает `certificate_invalid` (нас не пустили к origin) и
  `tunnel_refused` (соединение оборвано), что даёт диагностируемый сигнал.
- Ограничение указано в README, в интерфейсе профиля устройства и в runbook.

## Тест

`shared/sniff` — разбор настоящего ClientHello, отказ на не-TLS и на неполном
сообщении. `TestUnmanagedSNIIsRejected`, `TestIngressRefusesNonTLS`.
В стенде — проверка «SNI вне набора правил отклонён на ingress».
