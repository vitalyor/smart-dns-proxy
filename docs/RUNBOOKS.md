# Runbooks

Каждый сценарий: что видно, что происходит на самом деле, что делать.
Общее правило системы — **fail closed для управления, fail operational для
трафика**: недействительная конфигурация никогда не заменяет работающую.

## Дерево диагностики

```
Сервис не открывается
├─ dig <домен> @ingress вернул IP ingress?
│  ├─ нет → раздел «DNS не подменяет домен»
│  └─ да ↓
├─ openssl s_client показывает сертификат origin?
│  ├─ нет / соединение рвётся → «Ingress отклоняет соединение»
│  └─ да ↓
├─ curl отдаёт ответ сервиса?
│  ├─ нет → «Egress не доходит до origin»
│  └─ да → проблема на стороне сервиса (регион аккаунта, cookies, репутация IP)
└─ обычные сайты тоже не открываются? → «Unbound недоступен»
```

---

## Панель недоступна

**Видно:** UI не открывается, в панели ничего не меняется.
**На самом деле:** ноды работают на last-known-good. DNS отвечает, действующие
и новые соединения проходят. Агенты переподключаются с экспоненциальной
задержкой и джиттером, ничего не удаляют и не перезапускают.

```bash
docker compose -f /opt/smartdns-panel/docker-compose.yml ps
docker compose -f /opt/smartdns-panel/docker-compose.yml logs --tail 100 panel-api
```

Если упала база — панель недоступна на чтение и запись, ноды не затронуты.
После восстановления в интерфейсе будут видны пропущенные heartbeat и
фактические применённые ревизии.

**Не делайте:** не пересоздавайте том `panelstate` — в нём CA и ключ подписи.

---

## DNS не подменяет домен

**Проверка:**

```bash
dig +short <домен> @<IP-ingress>        # ожидаем IP ingress
dig <домен> @<IP-ingress> | grep status # REFUSED → это ACL или лимит
```

| Что видно | Причина | Что делать |
|---|---|---|
| `REFUSED` | адрес клиента не в списке доступа | Настройки → Доступ к резолверу → добавить сеть |
| `REFUSED` при частых запросах | лимит частоты | поднять `dns_rate_limit_qps` |
| настоящий IP вместо ingress | домена нет в активной версии набора | Наборы правил → проверить записи, обновить, подтвердить |
| ответ есть, но старый | ревизия не выкачена | Ревизии → собрать и выкатить |
| `SERVFAIL` только для обычных доменов | Unbound недоступен | см. ниже |

Метрика `smartdns_dns_rejected_total{reason}` называет причину напрямую.

---

## Unbound недоступен

**Видно:** управляемые домены работают, обычные — `SERVFAIL`.
**Почему так:** frontend никогда не выдумывает ответ вместо неработающего
резолвера — ложный ответ хуже честной ошибки.

```bash
docker compose logs unbound --tail 50
docker compose exec unbound drill -Q @127.0.0.1 nlnetlabs.nl A
docker compose restart unbound
```

Если `SERVFAIL` только на конкретном домене — вероятна проваленная валидация
DNSSEC. Это правильное поведение: домен действительно отдаёт битые подписи.

---

## Ingress отклоняет соединение

**Видно:** TLS-рукопожатие обрывается.

```bash
docker compose logs sni-proxy --tail 50
curl -s http://127.0.0.1:9102/metrics | grep ingress_rejected
```

| `reason` | Что это | Что делать |
|---|---|---|
| `sni_not_managed` | домена нет в активной ревизии | добавить в набор правил и выкатить |
| `not_tls` | на порт 443 пришёл не TLS | проверьте, что клиент не ходит по HTTP |
| `no_sni` | клиент не прислал SNI или включён ECH | сервис не поддерживается, см. README |
| `invalid_sni` | IP-литерал или некорректное имя | ожидаемо, вмешательства не требует |
| `port_not_allowed` | порт вне списка сервиса | Сервисы → Разрешённые порты |
| `max_sessions` | достигнут лимит сессий | поднять лимит или добавить ingress-ноду |

Рост `sni_not_managed` при неизменной конфигурации означает, что ваш адрес
сканируют в поисках открытого прокси. Это отказ по замыслу.

## Egress не доходит до origin

```bash
docker compose logs egress-relay --tail 50
curl -s http://127.0.0.1:9103/metrics | grep egress_requests_total
```

| `result` | Причина | Что делать |
|---|---|---|
| `denied` | домен или порт вне allowlist ревизии | проверьте, что сервис действительно ссылается на этот набор |
| `resolve_blocked` | имя не резолвится или ведёт в приватный диапазон | проверьте `egress_resolver` в настройках |
| `dial_failed` | origin недоступен с egress | проверьте сеть провайдера egress |
| `no_client_cert` | ingress подключился без сертификата | ноды из разных панелей или сертификат отозван |

**Заблокированный IP egress.** Если origin отвечает 403 или капчей, это не
сетевая ошибка: проба покажет `certificate_invalid` либо успех с нежелательным
содержимым. Замените egress-ноду и проверьте репутацию адреса.

---

## Отказ egress-ноды

**Ожидаемое поведение:** существующие TCP-соединения через неё обрываются —
перенос установленного соединения не гарантируется. Новые соединения уходят на
резерв: локальная политика на ingress считает три неудачи подряд отказом и две
удачи подряд восстановлением, поэтому переключение работает и без панели.

Проверка: `curl -s http://127.0.0.1:9102/healthz` на ingress покажет строку по
каждому сервису со списком egress и их состоянием.

Ускорить переключение: уменьшить `probe_interval_sec` в политике группы.

---

## Отказ ingress-ноды

DNS-группа исключает ноду из новых ответов после порога отказов, но уже
закешированные клиентом ответы продолжают указывать на неё до истечения TTL.
Клиентский failover зависит от кеша и от ОС — два DNS-адреса не гарантируют
переключения.

Ускорить: снизить `dns_ttl` сервиса (минимум 30 с). Цена — рост числа запросов.

## Ревизия не применяется

**Видно:** в колонке «Ревизия» висит «ждёт #N».

```bash
docker compose logs node-agent --tail 100 | grep -E 'apply|error'
```

| Код | Причина | Что делать |
|---|---|---|
| `bad_signature` | ключ подписи не совпадает | панель восстановлена без ключевого материала — восстановите его из копии |
| `hash_mismatch` | артефакт изменился при передаче | пересоберите ревизию |
| `agent_too_old` | нужен более новый агент | обновите ноду |
| `validation_failed` | конфигурация не прошла локальную проверку | текст ошибки в панели; обычно пустая группа или сервис без egress |
| `restart_loop` | больше трёх попыток за десять минут | исправьте причину и выкатите **новую** ревизию — она снимает состояние `degraded` |

Ошибка на любом шаге оставляет активной прежнюю конфигурацию.

---

## Обновление списка сломало сервис

1. Наборы правил → нужный набор → История версий → предыдущая версия → Diff.
2. Подтвердите откат, активировав прежнюю версию.
3. Ревизии → Собрать и выкатить.

Профилактика: для критичных списков указывайте commit SHA или тег вместо ветки
и режим «с подтверждением». Автообновление ветки — цепочка поставок, которой
вы не управляете.

---

## Диск заполнен

Агент никогда не удаляет активную и предыдущую ревизии, даже при нехватке
места, и не принимает новый кандидат, если его некуда записать.

```bash
docker system df && docker system prune -f
du -sh /var/lib/docker/volumes/*agentstate*
```

На панели растут `health_samples`, `events` и `audit_events` — фоновая задача
чистит их пакетами по расписанию хранения.

---

## Расхождение часов

Недействительная по времени подпись или сертификат отклоняются, нода уходит в
`degraded`. Включите NTP: `timedatectl set-ntp true`, затем выкатите ревизию
заново.

---

## Утечка или компрометация токена регистрации

Токен одноразовый и живёт не дольше 30 минут. Если он ещё не использован —
Ноды → Токены регистрации → Отозвать. Если использован, значит нода уже
зарегистрирована: найдите её в списке, удалите, а сертификат будет отозван.

---

## Подозрение на компрометацию панели

1. Настройки → Безопасность → завершить все сессии, сменить пароль, проверить TOTP.
2. Журнал аудита: искать `enrollment_token_created`, `service.updated`,
   `settings.updated` от неизвестного актора.
3. Удалить все ноды и перерегистрировать с новым CA (удалить `ca.crt`/`ca.key`
   из тома панели и перезапустить). Это разрывает доверие ко всем старым
   сертификатам разом.
4. Сменить `PANEL_SECRET_KEY` и заново включить TOTP.
